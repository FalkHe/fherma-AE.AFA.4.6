# Reviewer guide

A single-player AI Dungeon Master for people who want to try D&D 5e without a group or prior rules knowledge. The binding brief is [135.md](135.md); [docs/general/requirement-map.md](docs/general/requirement-map.md) is the design-side map. This page points at the **code as it is today**. Run it with the [README quick start](README.md#quick-start); live play needs an `OPENROUTER_API_KEY` and an ingested SRD corpus (`app srd ingest`).

## How the agent works (read this first)

Every player turn runs one LangGraph flow with exactly five nodes, composed in [backend/app/modules/game/agent/graph.py](backend/app/modules/game/agent/graph.py) and implemented in [flow_nodes.py](backend/app/modules/game/agent/flow_nodes.py):

```text
START -> advance -> decide | execute | await_player | narrate -> advance -> ... -> END
```

- `advance` ([advance.py](backend/app/modules/game/agent/advance.py)) is the only scheduler: it reloads the authoritative situation and picks one typed effect ([effects.py](backend/app/modules/game/agent/effects.py)).
- `decide` ([decisions.py](backend/app/modules/game/agent/decisions.py)) asks the model for a structured decision. It may bind only two **read-only** aids, with a bounded call budget: `lookup_rule` (SRD RAG, [srd/service.py](backend/app/modules/srd/service.py) `search_rules`) and `recall_history` (semantic search over past narration, [playthrough/service.py](backend/app/modules/playthrough/service.py)). Every proposed operation is validated against the typed registry.
- `execute` runs one operation from the registry ([operations.py](backend/app/modules/game/agent/operations.py), [operations_world.py](backend/app/modules/game/agent/operations_world.py)); every handler calls `playthrough.service`, which owns dice ([playthrough/dice.py](backend/app/modules/playthrough/dice.py)), hit points, state validation and the transaction. **The LLM never rolls and never edits state**; it only chooses operations.
- `await_player` interrupts the graph for a roll or a choice (human-in-the-loop); the LangGraph Postgres checkpointer ([core/checkpointer/service.py](backend/app/core/checkpointer/service.py)) resumes the same thread on the next request.
- `narrate` ([narration.py](backend/app/modules/game/agent/narration.py)) is an unbound model call over public situation data and recorded evidence; `playthrough.service` persists the beat as an event.

Entry point: `POST /api/v1/game/runs/{runId}/turn` in [game/routes.py](backend/app/modules/game/routes.py) -> [game/service.py](backend/app/modules/game/service.py) `run_turn` (ownership check, checkpoint lifecycle). The module's [README](backend/app/modules/game/README.md) and [docs/general/game-flow.v2.md](docs/general/game-flow.v2.md) (with [examples](docs/general/game-flow.v2.examples.md)) give the full picture.

## Main requirements

| `135.md` requirement | Where to look | Current state |
|---|---|---|
| 1. Purpose, usefulness, target users | [App vision](docs/general/app-vision.md#purpose); [README](README.md) | Solo play in plain language; the DM handles rules and mechanics. |
| 2. Core functionality and user interactions | Game flow above; character creation agent with LangChain tools ([character/agent/](backend/app/modules/character/agent/), [character/service.py](backend/app/modules/character/service.py)); campaign runs, adventures, events ([playthrough/routes.py](backend/app/modules/playthrough/routes.py)); adventure content as static JSON ([backend/content/campaigns/](backend/content/campaigns/), [content module](backend/app/modules/content/)) | Implemented end to end: sign in, start a campaign run, create a character in a dialogue, enter an adventure, take free-form turns; the DM pauses for player rolls and choices. |
| 3. User interface | [App routes](frontend/src/App.tsx): `/` dashboard and `/runs/:runId` ([playthrough/routes/](frontend/src/modules/playthrough/routes/)), `/runs/:runId/create-character` ([character/routes/](frontend/src/modules/character/routes/)), `/runs/:runId/play` ([play/routes/PlayRoute.tsx](frontend/src/modules/play/routes/PlayRoute.tsx)) | React + Material UI client with auth, campaign/run management, character creation chat and the play screen (transcript, composer, pending prompt, dice chips — [play/components/](frontend/src/modules/play/components/), [play/hooks/](frontend/src/modules/play/hooks/)). Operator tasks (content validation, SRD ingest) are CLI-only on purpose. |
| 4. Tools, libraries, error handling, real-world use | [OpenRouter seam](backend/app/core/llm/service.py) (every chat/embedding/image call, missing key reported by name), [retry with backoff](backend/app/core/llm/retry.py), [error envelope](backend/app/core/errors.py) `{"error": {"code", "message", "details"}}`, typed `refused` results for expected mechanic failures ([game/README.md](backend/app/modules/game/README.md#persistence-rules)), [session/CSRF dependencies](backend/app/modules/auth/dependencies.py), Postgres-backed checkpoint resume | FastAPI + LangGraph + pgvector; state, sessions and checkpoints persist in PostgreSQL; the stack runs in Docker ([compose.yaml](compose.yaml), [Makefile](Makefile)). |
| 5. Documentation, examples, decisions | [Quick start](README.md#quick-start), [docs index](docs/README.md), [architecture](docs/architecture.md) and [general/architecture.md](docs/general/architecture.md), [data model](docs/general/model.md), [content authoring guide](docs/modules/content.md), per-module READMEs under [backend/app/modules/](backend/app/modules/) and [frontend/src/modules/](frontend/src/modules/), worked flow examples in [game-flow.v2.examples.md](docs/general/game-flow.v2.examples.md) | Setup, subsystem behaviour, common play scenarios and design decisions are documented; `docs/roadmap/` is history, not current state. |

Tests: `make test` — 144 backend pytest files under [backend/tests/](backend/tests/) mirroring the modules (engine-free; `filterwarnings = error`), Vitest suites next to the frontend components. Opt-in DB-backed tests: `make backend-test-db`.

## Optional tasks claimed

| `135.md` task | Where to look | Current state |
|---|---|---|
| Medium 2 — short/long-term memory | LangGraph Postgres checkpointer ([core/checkpointer/](backend/app/core/checkpointer/)) for the per-run thread; `recall_history` aid in [decisions.py](backend/app/modules/game/agent/decisions.py) over embedded narration events ([playthrough/service.py](backend/app/modules/playthrough/service.py)) | Implemented: short-term = checkpoint state, long-term = semantic recall over the event stream. |
| Medium 4 — authentication and personalisation | [auth module](backend/app/modules/auth/) (Argon2, opaque server-side sessions, HttpOnly cookie, CSRF header), [users](backend/app/modules/users/), [auth UI](frontend/src/modules/auth/); every run/turn route resolves ownership through `user_id` | Implemented: accounts and user-owned campaign runs with their own characters and transcripts. |
| Medium 8 — security guard, dev/user split | [auth/dependencies.py](backend/app/modules/auth/dependencies.py) (`CurrentAuth`, `CsrfAuth`), ownership checks in [playthrough/service.py](backend/app/modules/playthrough/service.py) and [game/service.py](backend/app/modules/game/service.py); decisions restricted to a typed operation registry with a bounded aid budget | There is **no prompt-injection filter**. Misuse protection rests on authentication, CSRF and ownership boundaries plus the fact that the model can only pick validated operations. Model and prompt configuration is operator-side (`.env`, [core/prompts/](backend/app/core/prompts/)); there is no in-app developer settings drawer. |
| Hard 1 — agentic RAG | `lookup_rule` in [decisions.py](backend/app/modules/game/agent/decisions.py); [srd/service.py](backend/app/modules/srd/service.py) `search_rules` over pgvector; ingest CLI in [srd/commands.py](backend/app/modules/srd/commands.py) | Implemented: the DM decides when to consult the SRD and may query several times within a budget; only SRD text goes through RAG. |
| Hard 2 — observability | [core/tracing/service.py](backend/app/core/tracing/service.py) (Langfuse), applied through `langchain_config()` in [game/agent/model_call.py](backend/app/modules/game/agent/model_call.py) and [character/service.py](backend/app/modules/character/service.py); configuration in [.env.dist](.env.dist) | Implemented: Langfuse traces every chat, embedding and image call when the three `LANGFUSE_*` variables are set; blank means off. LangSmith is optional and purely env-driven (`LANGSMITH_*` in `.env.dist`), not wired in code. |
| Medium 1 — token usage and cost | Usage accumulated per node in [flow_nodes.py](backend/app/modules/game/agent/flow_nodes.py) / [effects.py](backend/app/modules/game/agent/effects.py); `run_cost` in [playthrough/service.py](backend/app/modules/playthrough/service.py); `app playthrough cost` in [playthrough/commands.py](backend/app/modules/playthrough/commands.py) | Partial: captured per turn and per run, queryable by CLI, not shown in the player UI. |

Not claimed: personality/tone selection, user-selectable models or sampling settings, a help chatbot, external-API tools, response ratings, tool toggles/plugins, a Ragas/DeepEval report, learning from feedback. Where [requirement-map.md](docs/general/requirement-map.md) or [general/architecture.md](docs/general/architecture.md) mention a developer drawer or DM tone, that is design intent, not shipped code.
