# Phase 6 — Catalogue depth: researched identity & real prices

**Goal:** make the catalogue's own numbers researched rather than guessed or claimed — structured model identity (manufacturer, model name, year range, type codes, trims) and real used-market prices.

**Status:** the identity track and the fencing hardening landed and are live end-to-end (steps 6.9–6.21, 6.24–6.27; milestones M1 and M2 verified and tagged); the used-price track stopped after storage — the research CLI (6.22), the estimator/API wiring (6.23) and the customer wiring (6.28) never landed, so no price snapshot is ever produced, and the docs and QA acceptance steps (6.29–6.31) never ran. `phase-6-done` is not tagged. Step numbering starts at 6.9 by design: 6.1–6.8 are the roadmap's *themes*, re-sliced into steps 6.9–6.31 (see the Theme mapping table); theme 6.8's premise was refuted at slicing time and folded into 6.14.

## Delivered
- **Structured identity on every catalogue row** — `buildingline`, `model_name`, `year_from`/`year_to`, `type_codes` and `variants` (trims) added as columns, with one validation module enforcing caps and normalisation; the old free-text `motorbikes.name` was renamed `query_name` (it is the phrase an admin typed, not a name).
- **One writer, one renderer** — `product_service.assign_identity` is the sole identity writer (extraction, CLI and the admin API all route through it, recomputing the path-shaped slug `bmw/r-1250-gs/2019-2023`); `naming_service` is the sole place parts become a display string, escalating buildingline → model → model + year range and adding the year range only where two rows would otherwise collide.
- **Approval now requires a complete identity** — a 422 `incomplete-identity` refusal in the service plus a database CHECK constraint, so no row reaches customers with a half-known name.
- **Ingestion researches identity, not just specs** — extraction fills the identity and trims from the fetched sources; the fetch stage starts from the suggestion's own links; claimed type codes become extra search terms; a source that contradicts a claimed year range or code raises a visible warning on the run instead of silently overwriting either side.
- **Backfill and cleanup CLI** — `app catalogue backfill-identity`, `set-identity`, `render-name`, `set-manufacturer`; all 16 previously approved rows were given a year range read out of their already-ingested source documents.
- **Manufacturer names canonicalised** against a committed known-marque list (`Kawasaki Motors` → `Kawasaki`), closing a Phase-5 open question.
- **Identity visible everywhere it matters** — name-based lookup gained a type-code leg, catalogue sort became composite (manufacturer → model → year), and all five advisor tools plus both API resources render the server-composed name.
- **Admin review screen for identity** — a new identity tab with claim shown beside finding, a trims editor, a live preview of the unsaved form, and buildingline autocomplete backed by a new endpoint; wired to a live `PATCH /api/products/{id}` identity block with regenerated typed client.
- **Prompt-injection fencing closed (M2)** — the page title and heading trail the advisor reads are now fenced and length-capped in the model-facing payload, proven live against a poisoned source document, with what is stored and served left byte-identical.
- **Used-price foundation** — `motorbike_used_prices` table (range, median, sample count, as-of date, per-source provenance), a read/write service with staleness logic, one config key `USED_PRICE_MAX_AGE_DAYS`, a `listing` source type quarantined from five code paths so asking prices can never enter the knowledge base or a spec extraction, and a stdlib `robots.txt` gate.
- **Used-price and trims UI built against fixtures** — the customer snapshot block (median, range, sources, date, stale wording) and the absent state exist and are tested; they render nothing today because no backend field feeds them.

## Non-obvious decisions
- **No classifieds scraper.** `robots.txt` for kleinanzeigen.de and mobile.de was fetched and disallows exactly the price-filter, sort and search paths a sampler needs. The design instead reuses the existing search → fetch → extract pipeline over URLs the search provider itself returned — so the product is honestly a *dated snapshot of published prices with visible sources*, not a statistical market sample.
- **Trims are JSONB spec deltas on the model row, never rows of their own** (owner decision), and no alias, buildingline or generation tables were added. Cheap and sufficient for display; the accepted cost is that spec filters match only the base row, recorded as a known gap.
- **A claim is never catalogue data.** The imported `suggestion` is an input hint and a reviewer comparison value only; it is exposed on the admin resource and on no customer-facing field, enforced by a compile-time test and an import-graph test.
- **Used prices sit outside the draft/verified approval split.** A used price is deliberately not presented as a fact — the date, the source list and the staleness caveat are the honesty mechanism, and adding an approval kind would have forced a change to the frozen promotion path.
- **Staleness is a caveat, never a refusal** — an old price is still used, with the date named and the word "indicative", because refusing leaves the customer with nothing.
- **Extraction fills gaps but never overwrites a human.** Re-ingestion merges under "an existing value wins" (type codes union), so an admin's correction is permanent without needing an "edited by human" flag.
- **The identity strings are deliberately *not* fenced**, unlike web prose: they pass an admin review gate before approval, and fencing a name would corrupt the string the advisor must say back to the customer.
- **The approval CHECK constraint was deliberately ordered late**, after the backfill and applied `NOT VALID` then validated in one migration — the openly stated exception to the phase's "model changes first" ordering, because existing approved rows would otherwise have failed the upgrade on day one.
- **Year ranges were never LLM-guessed.** Missing ranges were read out of each bike's already-stored source document with the sentence quoted in the step report; an invented year range would be an unverified number inside a customer-visible name.
- **Trim spec deltas travel the LLM wire as key/value pairs**, not a keyed map — a provider constraint discovered only on a live call (dynamically-keyed objects are rejected by strict structured output). Internal types are unchanged.
- **The `listing` quarantine was amended from four sites to five** mid-phase after a dev agent found a chunking path that would have written asking prices into the knowledge base — left unclosed, the final milestone would have appeared to pass while being provably false.

## Not delivered / deferred
- **`app prices research` / `app prices delete` (6.22)** — no CLI exists, so nothing ever writes a price snapshot. Consequence: the used-price table, its service, the robots gate and the customer UI block all have no production caller.
- **Researched price in the estimator and API (6.23)** — cost answers still fall back to MSRP/price band; the `usedPrice` block is absent from the generated API types.
- **Customer surfaces wired live (6.28)** — the frontend still carries local placeholder types for `usedPrice`, marked for deletion once 6.23 lands.
- **The three guessed demo prices** (BMW S 1000 XR, Honda CB500F, Suzuki GSR600) remain guesses; documentation must keep saying "not verified market data".
- **Quarantine carve-out 5** (excluding `listing` documents from `app chunks rebuild`) was assigned to 6.22 and is therefore still an open leak.
- **Documentation catch-up (6.29) and both QA acceptance gates (6.30 M3, 6.31 M4 + independent security proof)** never ran; `phase-6-done` is untagged. One M1 proof — a name escalating to include its year range — was deferred to 6.30 because the corpus contains no colliding pair, and so remains unproven live.
- **Two generic nameplate rows** (`Africa Twin`, `SV650`) carry names spanning several real generations; a per-generation split needs its own step.
- **Trim-aware filtering, buildingline as a table, per-trim type codes, per-trim provenance, `model_years`** — recorded under roadmap "Future upgrades", none scheduled.
- **The `a2Eligible`-vs-power consistency check and the concurrent-turn 409 race** — explicitly ruled out of scope, still open in earlier phases' notes. An observed advisor bug (a licence preference carried across turns and wrongly filtering) was recorded for a later phase.
